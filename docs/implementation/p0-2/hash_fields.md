# P0-2a 内容哈希字段

依据开发指南 v1.0 §3.4、§5.2 及大方案 v1.2 §5.1–5.5、附录 C。以下清单按已确认的科研语义归类，字段名仅使用规范已有写法。§5.2 要求逐对象维护字段表。规范尚未给出完整投影，附录 C 也只展示载荷片段。未定字段列入待决问题。

## 规范化

照录大方案 §5.2 的处理步骤及规则：

> 规范化步骤固定为：严格解析并拒绝重复键/NaN/Infinity → Schema 规定的缺省填充与字段投影 → 字符串 NFC 和 CRLF→LF → 领域十进制字符串规范化 → RFC 8785 JCS → UTF-8 → SHA-256。NFC、换行与十进制字符串是本系统的前处理规则，不是 JCS 自动提供的行为。
>
> 十进制字符串使用无指数、无多余末尾零、零统一为 `"0"` 的形式；有语义顺序的列表保持顺序，集合型列表去重后排序。

科研内容对象使用完整 SHA-256，标识使用类型与哈希版本命名空间。Danus 的旧 fact_id 仍在 `danus_fact:<id>` 命名空间。改变科研语义须创建新对象并重新批准。归属与授权按作用域检查并独立签名或审计。依据 §5.2。

## 逐对象字段

下表的「通用排除项」指注释、显示名称、缓存位置、运行状态、租户所有权和授权记录本身。它们不进入科研内容哈希。指向特定科学内容版本的引用与授予访问或批准的记录应分别辨认，具体引用投影以 R02 定稿为准。无独立科研内容哈希约定的记录仍可有其自己的签名、绑定摘要、审计哈希链或标识。

| 对象或动作 | 参与内容哈希的科研语义字段或已有绑定 | 不参与对应科研内容哈希的字段 | 依据 |

| Protocol | 数据快照、切分、指标、基线、调参空间、sanity 套件和适用模板。C.2 示例包括 `design_type`、`dataset_ref`、`metric`、`evaluation_unit`、`required_items`、`sanity_suite_ref`。 | 通用排除项。协议批准记录及批准状态不改写协议科学内容。 | §5.1–5.3、C.2 |

## 待决问题

1. **完整投影和规范化形状。** §5.2 给出通用规则，但尚未逐对象指定字段投影、缺省与可空规则、数组的有序/集合语义、标识与版本引用的表示。C.2–C.4 的字段示例不足以据此封闭 Schema。
2. **批准引用与科学绑定。** §5.1 要求 Prereg 绑定候选、批准与协议，§5.2 将内容身份与授权记录分开。需明确科学版本与阈值历史的哪些引用参与哈希，批准引用何时只用于授权核验。运行的资源上限与 `sanity_ref` 等绑定也需明确属于科学定义或资格校验。
3. **论断与审计记录的边界。** ClaimNode 六维中哪些初始值与来源引用进入内容标识、哪些由后续事件投影，规范尚未逐字段指定。EvidenceReport、EvidenceEvent、GateExecution 等是否另有独立内容标识及其与 §12.2 审计链的关系也待明确。
4. **发布签名载荷。** §2.4 要求签字绑定 `release_manifest_hash`，§5.1 又在 ReleaseManifest 概览中列出签字摘要。需明确签名前载荷、签名及回执的封装和计算范围。
