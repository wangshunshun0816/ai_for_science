一页总览

Danus-AI 帮助研究者把一个问题推进成有明确依据、范围与限制的研究成果。 它串联文献、选题、实验设计、代码实现、运行、证据审核、复现和报告；人负责选题、协议、价值判断和发布。

首版交付给单名研究操作者，一个个人租户可管理多个项目；数据和权限从第一版按租户划分，并用两个测试租户验隔离。首个完整场景是智能体/API 实验。使用现成模型承担理解与生成，使用程序控制权限、费用、数据、计算和状态。运行形态为一台 Linux 控制主机、按需启动的角色会话，以及本地或远程的隔离执行节点；Windows 用户通过 WSL2 使用。

1. 产品定位与首版范围

1.1 为谁解决什么问题

Danus-AI 面向需要实际开展研究、同时愿意审核关键决定的科研工作者。研究者常常需要在文献、脚本、模型调用、数据、实验记录和论文草稿之间反复转移信息。仅得到一个回答或一段代码，还无法判断它是否真正解决问题、比较是否公平、结果能否重算。

产品把这些工作接成有记录的研究过程。每个候选有来源和验证草案；每个实验有事先锁定的条件；每个结果能追到原始运行；每项正式结论都有范围和证据状态。失败、修改和人工干预也进入记录，便于继续研究和复核。

人承担四类科研决定：批准测量协议、选择具体课题、评价成果价值并定稿、签署最终发布物。系统在已批准范围内执行，不为每一次工具调用重新请求人工许可；超出预算、数据用途或科学设计时进入对应变更流程。

1.2 首版做什么，后续再做什么

范围 交付内容 边界
首版完整能力 智能体/API 研究的文献—选题—实验—证据—复现—报告闭环 任务须有可用协议、基线、数据和评测方法
首版独立功能 生成研究候选、评审已有课题 复用主流程，不自动进入确认实验

后续研究轨道 训练方法、模型架构及适用的其他学科 各自补齐任务模板、验证方法、基线和算力控制后开放
后续模型优化 某个窄任务的微调或独立强化学习试验 根据任务收益和完整成本立项，不是首版必经步骤

首版采用自托管、本地工作台与 CLI，不承诺多租户公共云、任意平台自动购买算力、所有科研领域通用或无人值守地保证发现。用户应具备运行 Linux/WSL2、管理模型账户和审核研究材料的能力。

后续市场形态面向多个个人研究者，每人拥有独立租户，并非多人团队。首版铺好账户/租户/项目、数据/凭证/费用和异步任务边界；未来托管仍需公网安全、强隔离、容量、备份和运营专项验收，不能承诺零改造。完整自主数学研究与 Lean 新能力后续建设，首版只保留受控兼容和引用。

1.3 怎样理解项目的三个目标

第一层是工程可执行：有权限边界，能限额运行、暂停、恢复和追溯。第二层是科研可靠性：在明确任务上，错误确认、有效发现和成本达到预先规定的标准。第三层是实际研究价值：结果是否帮助用户推进、调整或停止一项研究。

这三层分别验证。跑通流程不能证明更少犯错；通过受控评测不能保证每个新课题有价值；用户采用一项结果也不反过来证明它科学正确。工作台和成绩单会分开展示这些状态。

2. 用户如何完成一次研究

2.1 三个入口与固定出口

入口 用户提供 系统交付与停止位置
完整科研任务 问题、范围、已有材料、数据权限、资源上限和目标成果 推进完整流程；在人工关口等待，最后交付待签字成果
生成研究候选 背景问题、约束与候选上限 已检查的候选、排序理由和验证草案；停在人工选择前

2.2 贯穿案例：一种智能体策略是否值得采用

以下案例用于说明工作方式：研究者希望比较“带任务分解的执行策略”与现有基线，在受控工具任务中是否提高合规完成率，并满足预先约定的资源条件。

初始问题还不够精确。系统需要明确任务集合、质量指标、比较的模型版本、可用工具、可信终态与约束、方法和基线各自能用多少资源，以及什么程度的改善才值得采用。这里不预填一个看似通用的样本数或收益阈值，它们属于具体研究设计。

图 1：箭头表示研究推进与退回方向。协议已经批准且适用时可复用；证据不足、失败或没有候选均有合法出口。

2.3 从问题到候选：先把研究理由说清楚

系统先检索文献，把原文已有结果、存在的冲突和本次新推断分开。候选可以是“改变任务分解策略”，也可以是“减少无效工具调用”。每个候选附相关工作、可测预测、关键对照、可能失败的条件和最小验证草案。

候选检查回答的是：是否具备交给人选题的材料和可行路径。检索不到完全相同的论文，不足以证明全球首创；找到相似思路，也不能直接断言没有研究价值。数据接口、实现或费用不确定时，先用开发数据做小试点，确认能否开展实验。

通过检查后才排序。系统展示候选之间的取舍，保留未入选方案和理由。人批准的是一个具体候选版本及其研究范围。全部候选都不合适时，系统返回“没有可推进候选”，保存材料并结束本轮，不强行凑出课题。

2.4 从候选到正式实验：先决定怎么判断，再看结果

选题后，协议作者定义任务的测量方法、标准基线、数据切分和基本检查；分析设计者选择比较对象、主次指标和统计单位，引用人批准的最小有意义收益，并确定失败处理和停止规则。已有合格模板先检查适用条件；超出条件或科学影响不明时重新审核。

这些设计通过审核和必要批准后，形成锁定的预注册。方法实现者再开发代码，在允许的开发/验证数据上调试。正式运行前绑定代码、镜像、配置、数据版本及通过的健全性报告，不能在看到结果后再换一套更容易通过的规则。

案例中，如果任务分解策略使用了更多 token，协议就必须事先决定：比较相同预算下的质量，还是测量质量—成本关系。单看准确率提高，不能自动得出“策略更高效”的结论。

协议设计依靠有来源的组件、可信计分、独立参考和方法复核，再经 A7/A0 审核批准；不是通用模型凭提示词自写自评。既检查“算分是否正确”，也检查“指标是否回答问题”。无信息基线查异常，主要基线支持比较，消融分析组件贡献，三者不能混用。切分按实体、时间或模板及泛化目标设计，A9 保管隐藏数据。

协议确定后，A4 必须完成正式分析的跨字段核对和校准，再由 R06 锁定；模板超范围或缺独立参考时停在设计/探索，不能先确认再补依据。

2.5 从运行到成果：分别处理三类科学结果

可信执行程序收集原始输出，重算指标，保存全部尝试和费用。提交后依次检查记录与资格、统计支持、方法学问题。系统只有在全部条件满足时，才把限定范围的论断写入正式证据库。

案例结果 系统应怎样处理
有证据支持改善 写明任务、模型、资源与数据范围；不能扩大成“所有智能体任务都更好”
有证据排除达到目标的改善 形成有限否定，说明在已测条件下排除了多大收益；负结果同样可以有价值
样本、精度或设计不足 保留证据不足报告和下一步选项；不能改写成“已证明无效”

后续复现按事前规定的条件进行。重新运行相同代码、使用新独立数据、独立重新实现解决的问题不同，报告分别说明。人据证据、成本和实际用途决定定稿、补充实验或停止投入。

最终交付报告与制品包。任务完成不等于成果已经公开；只有人对具体最终版本签字后，才进入发布。用户也可以只下载成果自行保存。

3.2 实际部署：控制集中，执行隔离

部署基线是 Python 模块化单体控制服务＋独立角色会话＋隔离实验节点。控制服务统一处理权限、预算、业务状态和证据提交；耗时的模型请求、实验、分析和文稿编译由受限进程执行，网页请求不一直等待实验完成。

图 3：箭头表示受控通信。只有控制服务写业务数据库；模型角色和实验代码都不能直接访问数据库或提供商密钥。

部署单元 运行什么 最重要的边界
控制服务 管理 API、授权、对象状态、仓储与提交决策 唯一业务数据库写入进程
调度与角色宿主 任务领取、会话启动、挂起与恢复 通过服务接口更新状态，角色工作区相互隔离
模型调用代理 提供商适配、预算检查、调用与费用记录 集中保管 API 密钥；模型上下文看不到密钥
执行节点与任务容器 方法、基线、健全性和分析程序 容器只能看到被授权的数据与资源；不能控制宿主或任意联网
发布容器 报告整理、图表与 LaTeX 编译 只读脱敏快照，没有密钥与网络
数学兼容服务 原有数学记录及其验证路径 数学库仍由原数学路径管理，经验库只作受控引用

控制主机使用 Linux，Windows 通过 WSL2 的 Linux 文件系统运行；SQLite 数据库不放在 Windows 共享挂载或网络盘。远程管理走 SSH 隧道，首版不直接开放公网管理入口。执行节点可以本地部署，也可以是远程专用虚拟机，GPU 只在实际实验需要时接入。

初始控制面以 4 vCPU、8 GB 内存及适当 SSD 为测量起点。模型会话先并发 1，P2 真实负载通过后再启用最多 3；确认对照包初始并发 1。这些是待验证配置，不是吞吐承诺。

未来托管由浏览器访问，用户无需 WSL2。不可信租户的代码采用专属 VM 或同等已验证强隔离，再配任务容器；不能只用普通共享 Docker 容器声称租户安全。平台运维与租户科研审批分权，资源回收检查磁盘、日志和凭证残留。

3.3 技术选择的整体理由

Python 3.12 统一后端、实验和统计生态；FastAPI 提供管理接口，Pydantic 2 定义严格数据对象。SQLite WAL 适合首版单控制主机，配合事务减少状态与账本分裂；大文件使用按 SHA-256 摘要定位的制品目录，数据库保存引用和权限。

模型工具接口封装官方 MCP Python SDK，模型请求通过 HTTPX 和提供商适配器统一管理。接口协议负责传递调用，真正的权限由项目网关检查。实验用 Docker 隔离，远程传输用 OpenSSH/SFTP；统计使用经过独立校准的 NumPy/SciPy 算子。

界面采用本地打包的 HTML/CSS、原生 JavaScript、ECharts、KaTeX 和 Markdown 渲染组件。首版不额外引入向量数据库、Redis/Celery 或常驻前端服务。依赖选择围绕明确的使用规模，未来确有容量或能力证据时再调整。

代码与依赖、容器、提示词、模型配置、数据和分析脚本分别锁定版本。复用原 Danus 的检索、角色管理、隔离写作及数学适配经验；经验统计、预算、数据隔离和证据流水线按本项目要求实现。原仓库存在某个相似名称，不代表本项目功能已经具备。

SQLite 是本地交付基线，P0 在正式仓储开发前锁定后端。若明确纳入共享托管建设，优先评估 PostgreSQL 后再批准投入，不要求首版维护两套生产后端。迁移须验证事务、租约、幂等、归属和恢复，不能只换驱动。模型生产主线是自研薄循环加统一 API 代理，可使用合格的 DeepSeek/千问/Kimi/智普配置；不依赖 GPT 或 Codex CLI。

4.1 用户交互与成果层：看见过程，取得成果

R21｜报告与制品发布

4.2 研究规划与设计层：确定值得怎样研究

R03｜文献检索与论断卡片

技术与交接： A4 通过模型与严格对象契约提出设计，并使用合成/开发数据校准分析。草案送 R17，正式计划送 R06，统计算子由 R11 提供。它不读取实现者私有工作区或确认结果，不能根据已见结果偷偷修改原检验。

R17｜候选新颖性、可检验性与可行性检查

工作与产物： 检查候选的来源、差异、可测预测、关键对照、数据许可、算力与费用依据，返回“可推进、需修订、阻塞”及具体理由。

R16｜主编排与研究策略

工作与产物： 按任务状态安排下一步，生成指派建议、候选排序、阻塞处理和策略摘要。它保留完整候选池与选择理由，帮助人决定做什么。

实现边界： 动态工作由结构化 TaskPlan 组织：A1 提案，程序查依赖/权限/资格，A8 调度，R14 执行。可拆分、并行、重排和重规划；科学关口、根预算和暴露历史不变。版本冲突及取消中任务需明确对账，旧结果不能自动移入新计划。

R15a｜协议作者运行合同

工作与产物： 独立 A3 为一类任务定义怎么测量：指标代码、标准基线、调参空间、切分规则、已知答案和健全性套件，连同适用条件一起交付。

技术与交接： 模型辅助设计，Python 实现可执行测量与参考检查；开发数据上的基线验证经 R08 运行。产物进入 R04b，再经 R12 和 A0 审核批准。协议作者不能在使用该协议的同族研究中兼任分析或方法实现。

实现边界： 自主范围分复用、适配和新协议建设；每类单独验资格。缺独立参考或适用性依据时诚实阻塞。首包由人工先建，P4 再接合格 A3，不把模型自评当测量有效性。

R04b｜评测协议库

技术与交接： SQLite 保存状态与引用，制品目录保存不可变协议内容和测量代码。接收 R15a 的产物，为 R06、R10a、R08 和评测 R22 提供测量依据。文字澄清与科学变更走不同路径；影响无法确定时转完整审核。

实现边界： 协议包一并保存适用条件、来源/许可、可执行计分、三类基线、切分、正反样例、独立参考、环境和批准。首包集中在受控工具环境的智能体/API 比较；外部基准只作为候选组件，需准入与本地验证。

R06｜预注册与统计计划

工作与产物： 把已选候选、批准协议、分析计划、问题与阈值历史、假设族、数据暴露及随机性目标绑定并锁定，形成正式实验的判断依据。

技术与交接： Pydantic 跨对象校验、数据库事务与内容哈希；读取 R05/R04b/R08c、审核及预算条件，向 R08 和 R11 提供锁定计划。已见确认反馈后的修改形成新设计与相应新数据安排，不覆盖旧记录。

4.3 角色与实验执行层：让计划变成可信运行

R14｜Agent 角色运行时：执行、状态保存与暂停恢复

工作与产物： 启动单次角色会话，控制消息、工具调用、轮次、超时和交接；中断后能从已记录状态继续，而不是丢失上下文后重新付费执行。

技术与交接： 首版默认薄循环宿主，模型请求经 R08、工具经 R09，身份任务由 R08b 分配，为 R15a/b/c、R16 和审计/写作角色提供运行能力。决策轮、调用数、工具数和实验次数分开计数；长实验等待不等同于持续占用模型会话。

实现边界： “持久”指任务、轮次、工具请求、运行引用和停止原因可保存恢复，不是模型常驻。脚本化角色是预设动作的工程测试替身，不证明模型能力。上下文先保关键批准/状态/停止，再装授权证据，最后压缩历史；额度与输出预留按任务和模型实测。

R08b｜持久调度与角色互斥

工作与产物： 保存任务队列，分派有效租约，执行同族角色互斥和各实验组的可比额度；处理过期工作者、排队与重新领取。

技术与交接： SQLite job 表、租约与递增执行令牌，不另建消息队列平台。接收 R16/R14/R08 的任务，经 R07/R08c 条件检查后调度。已启动且不能中断的对照包优先；其余探索、确认、复现按份额轮转并提升等待任务优先级，不能因此挪用保护预算。

实现边界： 外层按租户与全局容量分配，内层保持科研队列和 Arm 公平。计划节点由服务分配身份，A1 不直接启动实例；换计划或会话不重置根任务额度。

R08｜执行器、模型调用代理与运行台账

工作与产物： 协调科研实验和角色模型请求，收集原始输出、计算标准指标、记录尝试与用量。进程退出正常但制品缺失，不能登记为有效成功。

技术与交接： Python 协调器、HTTPX 提供商适配、可信评测程序、Docker 节点客户端和制品收集器。科研运行先核对 R06 计划、R08c 数据授权、R08b 配额、R07 预占和 R10a 报告，再经 R24a 取得资源；输出交 R13，费用交 R07。标签与计分在可信路径处理，方法自报的准确率不具权威性。

R24a｜最小算力接入

工作与产物： 接入已准入的本地或远程执行节点，核对硬件、镜像与资源上限，完成运行、制品传输、停止及释放状态核查。

技术与交接： OpenSSH/SFTP、固定主机密钥、节点代理及容器配置。受 R08 调用，费用与租约回到 R07。首版只实现可核验的资源接入，不建设任意云平台自动采购系统；无法确认费用停止时仍保留计费待核状态。

4.4 证据验证与生命周期层：判断结果并持续维护

R10a｜健全性检查

工作与产物： 在正式运行前，检查输出解析、标签映射、重复关系、指标边界、token 计数及已知答案等基本性质，给出绑定代码、镜像和协议的报告。

技术与交接： Python 测试和小型参考任务，通过 R08 在合成/开发数据上运行；套件来自 R04b，报告是确认实验的前置。影响结果的代码或配置变化使报告失效。通过只表示已覆盖检查项合格，不证明没有任何 bug。

实现边界： 套件分通用、协议专属和轨道专属。重复试验不一律删除；不适用要有合同依据。每项记录通过、缺陷、执行错误、不适用或未覆盖；确认必需项出错/缺口不能过门。报告绑定准确协议、套件、数据、代码、环境和配置，变化后核验失效。

R10｜G0 确定性预检

工作与产物： 重建提交所引用的版本、运行和样本，检查批准、时间、哈希、全量尝试、预算公平及暴露记录，并重算可确定的指标。

技术与交接： 严格契约、哈希与确定性检查器；由 R13 调用，读取权威运行和锁定对象，输出逐项处置。探索与确认共享检查实现但使用不同配置，探索通过不能冒充正式通过；语义未知项转补证或审核，不自动当作符合。

R11｜G1 统计与允许措辞

工作与产物： 根据事先锁定的统计目标，计算效应、区间、多重比较和适用条件，给出能否支持改善、有限否定或其他限定陈述的依据。

技术与交接： NumPy/SciPy 与受信算子注册表；分析以版本化纯函数运行，读取 R06 计划和 R08 可信数据，向 R13 输出统计报告。A4 选择方法，不自行提交一个 p 值充当计算结果；新增分析方法先经独立参考与校准，条件不满足则报告无法可靠推断。

R12｜G2 方法学审计

工作与产物： 检查机械核验难以覆盖的设计、混杂、解释、范围和引用问题，返回阻塞问题、需补证或未发现阻塞问题，并给出依据。

技术与交接： 冷启动模型会话、严格审核契约与冻结材料包。候选检查允许同供应商的独立上下文；正式协议/分析和经验提交按规定保持供应商及底座独立。服务 R17、R04b、R06 与 R13；审计模型不能运行送审代码、改变数据或单独接受论断。

R13｜提交门与证据事务

工作与产物： 汇总 G0/G1/G2、版本与资格条件，决定接受、拒绝、补证或系统错误，并保存完整报告。它是经验论断和后续证据事件的唯一业务提交入口。

技术与交接： Python 确定性状态机和 SQLite 事务；通过后调用 R04 仓储，触发 R19 传播及后续复现。A6 是运行这条程序流水线的服务身份，不能另开写入路径。被拒提交仍有报告；模型“认为合理”不能覆盖硬性拒绝。

R18｜复现与适用的规模验证

工作与产物： 按锁定计划安排新运行随机性、新独立样本或独立实现的复核，记录每种复现的实际边界；有规模主张时验证事先指定的额外规模点。

技术与交接： 程序化计划执行器，调用 R08/R10a/R11，经 R13 提交新证据。它接收已接受论断及批准预算，不搜索有利种子，也不统一要求“再显著一次”。资源不足为复现待完成，不等于原主张已被推翻。

R19｜证据传播、矛盾与复审计

工作与产物： 维护依赖关系与当前有效状态。前提失效时找出受影响后继，限制新的使用，并建立有负责人、下一动作、预算和截止时间的复审计任务。

技术与交接： Python 图遍历、事件消费与数据库派生视图，读取 R04/R13 事件，将状态呈现给 R16/R20/R21。比较两项研究先判断目标与范围是否可比；新样本可以可比，样本不必重叠。状态变更仍经 R13，不直接改掉历史论断。

4.5 数据契约与研究资产层：保持统一事实来源

R02｜契约与金样例

工作与产物： 定义任务、候选、协议、运行、提交等对象必须包含什么，字段的单位、权限、锁定和状态转换如何约束；给出预期已知的正确与错误样例。

技术与交接： Pydantic 2 严格模型、JSON Schema、Python 接口和内容规范化。所有模块依赖它交换数据；契约本身不依赖业务实现。样例的正确答案先由独立依据确定，不能让待测系统生成自己的金标准。

实现边界： 新增租户/委派、任务计划/版本、检查报告和上下文/资格引用。服务端身份不由模型填写；科研哈希和访问权限分开，两个租户相同内容也不能互读。

R05｜工作材料与全局记忆

工作与产物： 保存背景、候选、设计草稿、选择历史、失败经验和用户使用记录，让后续任务能够在授权范围内复用已有工作。

技术与交接： SQLite 索引、版本化文件和制品引用；向 R03、R15、R16、R17 提供材料。事实、原因假设、可排除事项和验证状态分开。记忆查询也执行数据隔离，不能把当前确认结果换个名字送回分析者。这里的“全局”不表示所有角色都能读取全部内容。

实现边界： R14 保存执行状态，R05 保存工作记忆，R03 保存来源，协议/运行/论断等仍由各自服务负责。摘要有来源、版本和失效规则；授权撤销、删除与恢复联动索引/缓存/备份。失败解释不能直接当科学否定，记忆保存不自动允许模型训练。

R04｜经验论断存储

工作与产物： 保存正式接受的陈述、适用范围、证据强度及后续事件，支持有效论断查询；工作草稿和文献记载不自动进入这一层。

技术与交接： SQLite 事务仓储与不可变制品引用。只接受 R13 内部合法命令，为 R19、R20、R21 提供证据；数学记录通过只读引用保持来源权威。结果被撤销时保留历史与事件，不通过删除旧记录掩盖变化。

4.6 贯穿治理：预算、数据和权限

R07｜预算与费用账本

工作与产物： 在调用和租赁之前报价与预占，完成后结算，未知账单进入对账；按项目、月份、用途和任务控制额度，保存失败与重试费用。

技术与交接： SQLite 原子事务、整数微货币单位与唯一用量键。R08、调度和选题报价都依赖它，R20/R22 读取费用。关口成本是账本派生视图，一次调用支撑多个关口时按预先规则分摊，不能生成第二份费用真账。

实现边界： 凭证、付款账户和费用绑定租户，BYOK 故障不能自动换平台密钥。真实成本、研究预算和未来客户售价分开；300 美元是单租户试运行预算示例。

R08c｜数据守门与暴露台账

工作与产物： 管理开发、验证、确认数据的读取、挂载、反馈和外发授权，记录谁接触过哪些材料及其用途；维护许可、敏感性、伦理适用性和地域要求。

技术与交接： 版本化清单、Python 属性策略、访问/暴露事务和隔离挂载。为 R08、R09、R05 和 R06 提供授权依据。能读取不代表能发给外部模型；内容扫描只作辅助，分类或授权未知时停止相应发送。

R09｜角色网关与管理入口

工作与产物： 统一接收用户管理动作和角色工具请求，校验真实身份、项目、对象版本、用途及批准，将请求交给相应模块。

技术与交接： FastAPI 管理 API、官方 MCP SDK 兼容层、短期令牌和装配入口。连接模型角色与全部受控业务能力；批准、增加预算和发布使用独立的人类管理接口。身份来自令牌而不是模型填写的角色名，隐藏工具菜单也不能代替服务端授权。

实现边界： 租户、代行账户、角色、项目和租约从可信会话解析；查询、下载、后台任务都检查。A2 无提交工具且直接请求仍被服务拒绝，R13/R04 再守权威写入边界。

4.7 工程与评测基础：让系统可建设、可验收

R00｜能力、成本与环境探针

工作与产物： 小规模测量候选模型的工具调用、结构化输出、角色任务表现及延迟费用，核查执行节点、容器和计费能力，形成准入依据。

技术与交接： Python、HTTPX 和固定小任务。P0 用人工限额、单并发脚本启动；R07/R08 完成后接入正式路径，早期账单导入。结果用于角色配置、预算和容量估算；缺少合格独立审计配置会阻塞正式确认，但不阻止低风险候选准备。

R01｜工程骨架、依赖与持续检查

工作与产物： 建立模块边界、安装与配置、依赖锁文件、数据库迁移、容器构建及自动检查，使后续功能按同一规则集成。

技术与交接： pytest、Ruff、mypy、GitHub Actions、Hypothesis 状态机测试；用 SBOM、镜像摘要和签名记录交付版本。它支撑全部模块，默认 CI 无真实付费凭证；真实资源测试走独立授权作业。检查代码依赖、并发竞态和故障恢复，而不只验证顺利路径。

R22｜系统评测与运维验收

工作与产物： 维护独立答案的评测驱动，开展缺陷包、协作、选题、产品效用和可验证性评价，输出可重算成绩单；同时执行健康检查、恢复与泄露演练。

技术与交接： Python 评测器、独立参考计算、统计校准和版本化逐题记录；调用已建业务模块，接收 R07 全部成本。P0 就开始准备，P6 汇总交付。被测系统看不到答案，不能用“系统自己接受了多少条”当作正确产出数。

实现边界： 除科研收益，逐角色、动态计划、协议有效性、双租户及上下文恢复分项验收；真实模型主/回退配置按任务类型登记资格。脚本通过与模型能力通过分开。

5. 角色协作与研究资料流转

5.1 人、模型和程序各承担什么

类别 角色 核心责任
人 A0 操作者 问题与资源授权、协议/选题批准、价值定稿、发布签字
模型 A1 编排器、A2 探索者 提出下一步与候选，组织有依据的探索
模型 A3 协议作者、A4 分析设计者、A5 实现者 分别定义怎么测、怎么判断、怎么实现
模型 A7 审计者、A12 隔离作者 审查方法学问题；按脱敏证据写作
程序 A6 证据流水线、A8 调度器、A9 数据守门人 执行计算与规则、任务租约、数据授权
程序 A10 复现器、A11 发布闸门 按锁定计划复核；检查签字后交付

角色是责任身份，不是永久占用的一台模型服务。模型会话按需启动，可使用同一类模型，但工作区、可见材料和工具权限必须满足任务规则。A4 与 A5 在同族任务中分开，A3 不参与其协议所服务的同族分析或实现；A7 冷启动审查，不继承作者的私有对话。

候选审核可以同厂商独立会话；正式协议/分析审核相对作者、经验提交审核相对实现者及被测模型，须满足规定的供应商与底座分离。缺少合格配置时暂停相应确认，不能用“换了一个提示词”冒充独立审查。跨厂商本身也不证明判断统计独立，实际效果仍由评测检验。

单操作者可以兼做问题提出与批准，但必须如实标记单人模式。另建一个账号不等于外部独立审核。人若读取隐藏测试材料，同样记录暴露并限制其后续确认用途。

详细开发与测试按《Agent 角色实现与验收规格》v0.2执行。角色、任务实例、程序服务和共享运行时分别建模；每类角色交付合同、上下文、输出校验、异常处理和资格证据。

5.2 资料沿着什么链条流动

研究资料的主链为：任务 → 候选及版本 → 选择决定 → 协议与预注册 → 运行及全部尝试 → 提交与审核报告 → 有效论断及证据事件 → 发布快照。

资料区 存放什么 能否作为已验证结论
工作材料 文献、候选、草稿、探索结果、失败原因假设 不能自动视为真值，必须保留来源和状态
运行制品 代码、镜像引用、配置、原始输出、日志和分析输入 是可检查证据，进程成功不等于科学合格
正式证据库 通过提交门的限定陈述、证据与后续状态 按当前有效状态和范围使用
发布快照 某次定稿采用的证据、表图、披露和制品清单 对应具体版本，变化后重新检查和签字

内容摘要识别的是“这一份具体内容”，版本和引用保留其前后关系。科学语义变化形成新对象；撤销、降级等是追加事件，不原地改掉历史。模型只提交允许的字段，身份、费用和测量来源由可信服务补齐。

5.3 权威写入链为什么必须固定

经验论断的链条固定为 A6 服务身份 → R13 提交决策 → R04 存储。R13 综合检查后决定是否接受，R04 负责保存，不另设一套通过标准。写作、编排、审计模型都没有直接把自己的判断写成正式结论的权限。

大文件先校验并落到制品目录，业务引用与事件再通过事务提交；外部调用请求也留下可靠的待发送/回执记录。进程崩溃后依据这些记录恢复，而不是猜测调用有没有执行。重复请求凭幂等键识别；远端状态不明时先对账，避免重复购买或付费。

5.4 三种状态不能混用

一个任务可以按约定交付结束，但没有科学正结果；一个论断可以曾被支持，后来因错误被标记待复核；一个报告可以已经签署，但尚未公开。任务、证据和发布状态分别展示，避免“任务完成”被理解为“发现成立”。

项目自身的变更也分三维：决定是否批准、功能是否实现并验收、效果是否有证据。当前说明书解释的是设计；后续开发完成和正式成绩必须通过各自记录证明。

5.5 固定关口中的动态调用

任务完成或阻塞触发程序检查。下一步已确定时直接创建合法任务；需要研究判断时才调用 A1。A1 给出带版本、输入输出合同和依赖的计划，程序检查后由 A8 分配角色实例。可以并行检索和候选检查，也可以结束无结果分支；正式确认的指标、样本和停止规则不允许临时改动。

取消或改计划时，排队任务撤销，运行中任务明确继续/取消并核对费用；旧结果保留原历史，重新使用需验证资格。它既不是所有 Agent 固定串行一遍，也不是模型任意调工具。

6. 科研可靠性与运行控制

6.1 证据检查各管一件事

环节 要回答的问题 不能扩大成什么保证
健全性前置 指标、解析和基线等基本实现是否通过已知检查？ 方法完全没有 bug
G0 确定性检查 来源、版本、数据、全量尝试与数字是否一致合规？ 设计在科学上一定有效
G1 统计 在锁定目标与假设下，数据支持多大效应和范围？ 未测场景也成立
G2 方法学审计 是否存在尚未解决的混杂、解释或范围问题？ 模型没有发现问题就是证明
后续复现 在声明的新运行或新数据条件下能否支持结果？ 同实现重跑已经排除共同实现错误

前三个提交后关口与健全性报告共同支撑首次接受；后续复现增强或限制结论，不是每条首次提交必须先支付的重复实验。必要检查不能因为单次费用高就被删除；额外可选检查才按价值与预算排序。

6.2 怎样避免试到满意为止

开发数据用于探索，验证数据用于获准的实现调试，确认数据用于锁定后的检验。角色只获得相应材料；方法容器不直接读取隐藏答案，分析者不借失败记忆绕回当前确认结果。

系统同时记录“哪些尝试共同支持同一科学主张”和“为了选择方案看过哪些结果”。前者形成假设族，后者形成选择与暴露历史。换名字、换月份或换数据池不能自动清除同一主张的连续尝试；一般背景阅读也不意味着所有课题永久并成一族。

首版默认每族总 α=0.05、最多 3 个确认分析槽位，事前分配，槽位内处理多个主比较。后续尝试若受前次反馈影响，还要有符合要求的新确认数据。该规则不承诺所有未来项目合起来永远只有 5% 错误，也不把 3 个槽位解释为系统只能发现 3 项成果。

重复题目、同模板变体和同一数据上的多种子不能简单相乘成为独立样本。预注册必须说明结论针对指定随机实现、新随机性还是确定性任务；固定种子上的平均成绩不自动代表普遍平均表现。

6.3 正确结果、正确理由和失败经验

在案例中，策略提高了答案质量，仍可能因为增加了预算、使用了不同信息或其他未控制因素。性能结论与机制解释要分开验证。对机制研究，确认前列出竞争解释各自的预测或分布、能区分它们的观察或干预，以及什么结果仍然无法区分。

搜索得到一个有效配置可以是有限成果，不能直接写成理解了规律。解释锁定后，应在同一规律下的新隐藏样本中检验其预测；改变了世界规则的实例不适合作为同一公式的泛化测试。均值相同但分布不同也可能有区分价值，不能粗略判定“没有信息”。

失败记录保存事实与待验证原因。例如“运行超时”是工程事实，“方案复杂度过高”可能只是原因假设，“该科学方法无效”更不是自动结论。记录允许没有可排除的科学假设；需要复用为研究前提时，仍须有独立证据支持。

6.4 什么时候用 API，什么时候微调

首版需要语言能力的任务优先使用经过角色测试的现成模型 API，业务规则和统计算法由程序执行。选择具体模型由能力、费用、数据条件和独立性共同决定，业务代码不锁死品牌。

决策 必要条件
继续 API 质量和成本可接受，或尚未确定瓶颈来自模型；先处理工具、材料与流程问题
开展窄任务微调试验 稳定任务、明确质量/成本问题、合法且可核验的数据、独立留出及批准预算
替换生产模型 与当前配置及未微调底座比较后质量和关键错误合格；完整成本、时延、权限及旁路测试合格，有回退路径
开展强化学习 可验证奖励、可重复环境、多步目标与强基线，且能控制奖励漏洞、泄漏和总投入

完整成本包括数据整理、训练试错、验收、推理部署、运维更新和回退，按同一周期与 API 比较。“月费超过某个数”不足以自动触发微调。优先候选是卡片提取等窄任务，不能把健全性程序或证据核心交给未经验证的模型替代。

科研轨迹先按审计发现、工程错误、文献报告和独立核验结果分级积累。几十条确认轨迹不能宣称形成数据壁垒；API 输出能保存也不代表获准训练，使用前逐家核对条款。用户研究训练方法和 Agent 自身优化是两种项目，费用与排期分开。

6.7 数据与发布的安全边界

外发前按数据分类、角色、用途、目标提供商和地域授权，再检查实际文本及附件；未知或过期则阻止。容器默认不能任意联网，模型上下文没有 API 密钥；外部文献中的指令只是待处理内容，不改变系统权限。

关键事件有连续哈希与操作者控制的签名检查点，发布清单绑定代码、依赖清单、镜像和证据摘要。使用 Ed25519 签名、SBOM 和镜像核验帮助发现变更，但不宣称可以对抗同时控制应用、私钥和全部备份的攻击者。

SQLite 使用在线备份，每日及发布前保存适当快照；密钥泄露时撤销受影响凭证，停止新暴露与负债，再核对仍在运行的任务和未结账费用。恢复不仅是复制数据库，还包括外部资源、账单和证据资格检查。

原始输入依许可和保留策略保存，不承诺永久保留。租户数据删除要联动摘要、缓存、索引和备份策略；证据删除影响可复核性时限制依赖结论并保留必要受限审计信息。恢复不能让已撤销授权或已删除资料重新可见。

7. 成果交付与能力验证

7.1 用户最终拿到什么

一份完整项目交付包含研究问题和选择过程、正式协议与预注册、代码与环境清单、所有运行与费用摘要、主要结果与证据报告、复现类型、限制及可下载报告。制品包提供从报告数字追到运行和分析的对应关系，以及授权范围内的重算步骤。

没有正面发现，也应交付有限否定或不确定报告。受限数据不为满足“可复现”而违规公开，而是提供合法授权核验路径，并说明条件。任务结果与发布版本分别保存；旧发布发现问题后可撤回，历史证据仍可查。

7.2 五类评测分别回答什么

评测 核心问题 不能代替的东西
证据门校准 固定证据包中的缺陷能否拦住，合格包会不会误拒？ 整个系统的科研发现能力
a/b/c 协作比较 分权和约束的组合是否降低错误确认，并保持召回与成本？ 单个组件的独立因果贡献
选题能力 候选能否提出可检验思路，排序是否优于基线？ 新课题已被证明有科学价值
产品效用 对真实用户，完整流程是否改善质量、时间与投入？ 受控真值下的正确性评测
可验证性 发布材料能否定位、重算并在授权范围内核查？ 所有科学主张必然为真

参考证据包从已知机制、解析解或独立核查的实验建立；缺陷包在其上做明确修改。数字错配可以改报告，数据泄漏或不公平调参必须真的改变过程并留可信记录。真实论文的发表状态不能直接当金标准；有争议的参考单列。

7.3 假阳性、未确认与成本怎样比较

a 是单工作者，b 是协议、分析、实现分权且有健全性前置与对等预算，c 保留分权但不强制后两项。三组使用相同预分配任务、可用工具和总资源上限，由共同独立评分器评价；不能因 a/c 缺少 b 的程序步骤就预判其科学失败。

固定真/假命题和隐藏真值后，FPR 是全部假命题中被最终错误确认成立的比例；Recall 是全部真命题中被最终确认成立的比例。 未确认率为 1−Recall，包含错误否定、证据不足、超时、执行失败和预算耗尽；这些原因分开报告，主分母不删除系统自身失败。

b 对 a 的拟定正式成功条件要求同时满足：FPR 改善超过 2 个百分点的置信界限；Recall 的非劣界限为 5 个百分点；每项独立核验有效产出的成本比置信上界不超过 1.5。5 个百分点是明确的容许界限，不能宣传为已证明假阴性完全不增加。具体不等式和统计合同见原规格 10.6。

费用包含全部失败、重试和审核；有效产出由独立评测判定，不能把系统 accepted 数直接作为正确数。零有效产出不产生有限单位成本。费用与产出共同进入不确定性分析；首版使用有适用条件的保守方法，条件不满足只报实际账单与描述性结果，不强造区间。

样本设计针对三条件同时通过的目标联合功效，在事先声明的替代效应下争取至少 80%。小试跑用于估算成本和设计能力，不等于正式证明。成绩区分达标、证据不足与明确不利结果；低功效不自动判失败，也不豁免负面证据。

7.4 选题、产品价值和可验证性的独立检查

再发现评测给定背景和受控语料，隐藏目标论文及近重复答案，比较直接提问与结构化流程。MOOSE-Chem 提供这种构造思路；相似度反映再发现程度，不等于原创性或真实性。训练截止不明时披露污染风险，不假定论文较新就一定未见。

排序在冻结的完整候选池上独立盲评，再比较系统、简单规则和随机排序。只观察被选课题的后续结果会产生选择性观测，不能据此证明所有候选排得正确。DiscoveryWorld 可作为补充环境，但任务成功与解释评分分开；二者均分之差不能直接当 FPR，也不能凭均分差证明暴力搜索原因。

产品效用首选强基线 d2：研究者＋通用 Agent＋人工预注册与留出隔离，比较质量、人工分钟、总历时、费用和采用理由。无强制预注册的 d1 仅在另有问题和预算时增加。控制或记录任务难度、人员经验和重复做题的学习影响，不能刻意削弱基线。

可验证性由未参与原任务的人，按预先抽样规则使用正常发布物和授权材料核查。确定性分析按容差重算，随机模型按复现标准检查；临时作者帮助、缺失材料、失败、时间和费用都记录，不承诺任何研究都能在十分钟内完成科学核验。

8. 开发实施路线

8.1 为什么按这个顺序建设

先统一数据对象和权威记录，再建立受控执行，才有条件验证结果；证据闭环具备之后，再把多角色自动化接入完整流程。界面可以提前做原型，真正的写操作仍要等权限和底座验收。评测从 P0 开始准备，不等产品完成才临时寻找题目。

8.2 首轮 P0 怎样启动

首轮按最多 10 个工作日安排：先登记实际负责人、投入工时、首个问题和资源；固定参考源码与复用边界；制作合成案例和独立答案；在已批准额度内开展至多 3 例人工试跑；最后整理失败路径、成本与工程任务。

三例用于诊断接口、信息隔离和记录是否可执行，不用于估计稳定产能或证明协作收益。付费条件不足时先完成本地合成工件，实际调用保持未启动。P0 不要求尚未开发的完整平台，但最小限额、数据边界和全部记录必须存在。

确认后需要落实四项责任：产品负责人、实现集成负责人、统计/评测复核、部署/安全复核。可以兼任，但自审不称为外部独立验证。AI 辅助编写和检查，不能替代实际授权、科学判断与验收责任。

8.3 工期、投入与调整规则

完整范围的总工时在 P0 按工作包重新估算，纳入逐角色资格、动态计划、双租户隔离、首包独立参考及上下文治理；不沿用未覆盖这些增量的总数。工程工时、方法复核、机器历时、审批等待与正式评测费用分别计算，再由实际人员投入确定日期。

A0 暂按每周 2—4 小时预留，统计与安全复核各暂列 16—32 小时规划预留。不存在已经落实的免费人力假设；现实投入不同就重算排期。开发工时、机器运行、人工审核和日历等待分别记录，不能把模型生成很快等同于整个工程已经完成。

候选上限、角色轮次、并发、队列份额和预算分配进入参数台账，带负责人、观察窗口、预算与决策点。诊断在独立开发任务上进行，不能拿正式留出反复调到通过。资源不足时延期扩展轨道、自有模型训练、额外规模点和界面美化，保留权限、预算、隔离及必要证据检查。

8.4 最终怎样决定可以交付

工程交付需验证正常路径，也要验证并发抢预算、旧租约回传、进程崩溃、外发越权、密钥撤销、孤儿资源、恢复对账和发布制品变化。科学组件需要独立参考和校准，用户还应能完成三个入口及必要审批。

工程通过但协作收益证据不足时，可以交付清楚标记的受监督验证版；不能因此宣称已经达到科研收益目标。真实试点没有正结果仍可交付诚实报告；正式公开发布由人对具体版本签字。

首版之后，再按每条轨道的任务模板、测量与分析、健全性、基线、数据许可和算力阶梯接入训练、架构等研究。API、微调和强化学习继续按任务准入；数学形式验证另经 Lean/Mathlib 的实际检查，不把经验统计与形式证明硬套成同一证据标准。
